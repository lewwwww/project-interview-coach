# 代码证据映射（Code Evidence Map）

> 本文件是 skill 的护城河：把项目描述/简历里的每一条声明，落到具体代码路径，并给出证据分级。面试深挖的弹药全部从这里来。

## 四级证据分级

| 分级 | 含义 | 判定方式 |
|---|---|---|
| **已核验** | 运行/测试/命令直接观察到的 | 启动过服务、跑过测试、执行过命令、看过真实输出 |
| **代码支撑** | 代码或配置直接支持，但未运行 | 文件/函数/调用链存在，逻辑成立 |
| **推断** | 合理推断，仍需确认 | 从上下文推理，没直接看到 |
| **未核验** | 描述/简历声称，无证据 | 找不到代码，或只有口头说法 |

## 输入来源（声明从哪来）

阶段 1 收集的「项目描述 / 简历」是本流程的输入，**获取方式分工**：

1. **简历 → skill 自己读**：默认按 SKILL.md「笔记库接入」实时读取最新版简历（`投递策略\简历\` 下的最新 docx，按目标岗位选央国企版或开发版），用户**不用**在对话里贴；读不到才让用户提供。
2. **项目描述 → 简历自带或用户给**：简历里的「项目经历」就是现成项目描述，自动提取即可；若目标项目**还没进简历**（如刚学的新项目），需用户在对话中提供一段描述（3-5 句），或先转 Skill A 产出。
3. **学习笔记 → skill 自动读（Skill A 产物）**：若 `<你的笔记库>\学习中\<项目名>学习笔记.md` 存在（project-learning-coach 项目学习器产出），自动读取——其中「项目描述」段可直接作输入；12 节学习内容提供代码锚点、业务理解与场景题素材，**优先于从零跑代码探索**；不存在则跳过。
4. **代码路径 → 必须用户给**：skill 无法自己定位项目代码，项目路径/代码仓库位置由用户在对话中明确提供（阶段 1 收集）。

## 映射流程（阶段 2 执行）

1. **提取声明**：把项目描述/简历拆成一条条可验证的声明（动词 + 对象 + 数字）。
   例：「独立负责订单模块，数据库条件扣减防超卖」→ 声明 A「独立负责订单模块」、声明 B「防超卖用数据库条件扣减」。
2. **代码定位**：为每条声明找代码锚点——文件路径 + 类/函数 + 关键调用链。
   - 声明 B → `OrderServiceImpl.submit()` 里 `UPDATE ... SET stock = stock - n WHERE stock >= n`。
3. **分级**：按上表判定。
4. **设计追问链**：每条声明配 1-2 个追问点（面试官可能怎么深挖）。
   - 防超卖 → 追问「条件扣减失败怎么办？高并发下会不会超卖？乐观锁和悲观锁为什么选这个？」

## 证据映射表（输出格式）

```markdown
| 声明 | 代码路径 | 分级 | 追问点 |
|---|---|---|---|
| 独立负责订单模块 | OrderController / OrderServiceImpl | 代码支撑 | 订单状态机谁设计的？状态流转在哪？ |
| 防超卖：条件扣减 | OrderServiceImpl.submit() L42 | 已核验（压测跑过） | 并发下兜底？库存为负怎么防？ |
| 搭建三层架构 | controller / service / mapper 三包 | 已核验 | 为什么分层？直接调 Mapper 行不行？ |
```

## 常见陷阱与处理

| 陷阱 | 处理 |
|---|---|
| 声明带大数字（QPS/万级） | 追问来源：压测报告？日志？估算？没有来源 → 降级为定性描述或未核验 |
| 用「我们」模糊 ownership | 追问「你具体负责哪部分？代码哪些是你写的？」→ 收窄到真实边界 |
| 抽象名词（高可用/高性能） | 要求落到具体机制（重试？降级？缓存？）→ 找不到代码就是未核验 |
| 简历写了但代码里没有 | 诚实收窄：删掉 or 补证据 or 用边界话术 |

## 诚实边界话术（面试可用）

- 「这部分不是我主要负责的，我能讲清它和我负责模块之间的调用与数据流；我实际完成的是……」
- 「仓库能确认当前实现，但选型过程不能只凭代码确认，我会把能看到的取舍和我的理解分开说。」
- 「这个指标我简历里写了，但现有材料没有测试报告支撑。面试前我会补证据，否则我会弱化成可验证的结果。」

## 硬规则

- 代码可以证明实现，但**通常不能证明个人 ownership 或生产影响**——ownership 靠用户自述+代码归属推断，标注清楚。
- 可疑模式是「风险/可能的改进点」，不是「历史 bug」——没有提交记录/issue/日志支撑就不写成已发生的事故。
- 把「当前实现」和「建议改进」分开，不把没做的说成做了。
